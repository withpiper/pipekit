## F2 — `pk promote` writes terminal Linear state at PR-open, not at merge

**Status:** Documented behavior since v2.3.0. Semantically louder in v2.5.0+ because state names now imply "code is on env X" rather than the looser `Released`.

**Observed.** Running `pk promote beta --confirmed`:

1. Opens the dev → beta promote PR.
2. **Immediately** writes Linear `In Dev → In Beta` for all bundled issues.
3. Prints "Open the PR in browser and merge with 'Create a merge commit'."

Empirical timing gap from the 2026-05-15 Piper canary: **~5 minutes** between `pk promote` writing the state and the PR actually merging.

**Why it matters.**

- For the gap window, Linear shows the WIT in the destination env's state while the code is still on the source env.
- If the promote PR is held up (CI flake, reviewer feedback, decision to abort), Linear is ahead of reality.
- In v2.4.x this was the `Released` state and felt vague enough that the lie was tolerable. In v2.5.0+, `In Beta` literally means "the code is on beta" — which isn't true until the merge.
- Aborted promotes require manual Linear revert before re-running.

**Severity.** Medium. Not blocking; recoverable; documented. But the v2.5.0 rename made the lie semantically louder, and the canary confirmed the gap is non-trivial.

**Resolution options.**

1. **Two-phase transition.** `pk promote` writes an interim state at PR-open (e.g. `Promoting to <Env>` or stays in current state), then a separate post-merge hook (or `pk promote --finish`) writes the terminal state. Mirrors the `pk ship` → `pk done` split for the first hop.
2. **Wait-and-watch.** `pk promote main --confirmed --wait` blocks until the PR merges, then transitions. Trades CLI ergonomics for correctness. Needs an interrupt-safe state file so re-running picks up where it left off.
3. **Webhook-driven.** GitHub Action on promote-PR merge calls a small endpoint that flips Linear. Most accurate; most infrastructure to set up.

**Recommendation.** Option 1 (two-phase) — cleanest model, matches existing `pk ship`/`pk done` split, doesn't require new infra.

## pk_promote — over-eager WIT-mention matching

**Status:** New finding from 2026-05-15 Piper canary.

**Observed.** `pk promote main --confirmed` saw 47 bundled commits and tried to transition 6 WITs (`WIT-415, 416, 417, 418, 434, 459`) that were in `Ideas` or `Approved` state. The leap-frog guard (`pk_linear_set_state advance` mode) correctly refused, logging "refusing leap-frog to 'Done'" for each. Net effect: no harm done, but:

- 6 false-positive transition attempts in the promote output.
- Each one made an extra Linear API call (fetch current state, compare ranks, log refusal).
- If the leapfrog guard ever has a bug, those WITs would be wrongly advanced past UAT without ever being worked on.

**Root cause.** `cmd_promote` scrapes all `<prefix>-NNN` mentions from commit message body + title via:

```bash
issue_ids=$(git log "origin/$target..origin/$source" --pretty=format:%s%n%b 2>/dev/null \
  | grep -oE "${issue_prefix}-[0-9]+" | sort -u)
```

This catches every WIT reference, including:

- Cross-references in commit bodies (`"depends on WIT-417"`, `"blocks WIT-415"`)
- "See also" mentions
- Issues referenced in commit checklists or AC excerpts

…not just the WITs whose work actually shipped in this bundle.

**Why it matters.**

- Noise in promote output makes it harder to spot real issues.
- The leapfrog guard becomes the primary filter rather than defense-in-depth.
- Any future regression in `pk_linear_set_state advance` would silently advance WITs that were never worked on.

**Severity.** Medium. The leapfrog guard is the safety net; this is about reducing reliance on it.

**Resolution options.**

1. **Strict ownership match.** Only transition WITs whose ID appears in a commit's *title* with an ownership prefix (`feat(scope): WIT-XYZ ...`, `fix(scope): WIT-XYZ ...`) OR in a recognized GitHub closing keyword (`Closes WIT-XYZ`, `Fixes WIT-XYZ`, `Resolves WIT-XYZ`).
2. **Branch-name match.** Only transition the WIT whose ID appears in the feature branch name (`feature/WIT-XYZ-<slug>`). Cuts cross-references entirely. But misses legitimate bundled WITs that happen to ship together (multi-WIT branches, follow-up PRs to dev).
3. **Hybrid.** Strict ownership match (option 1) by default. Optional `--include-mentions` flag for the rare case where bare-mention is desired.

**Recommendation.** Option 1 (strict ownership match). Closing-keyword convention is well-known (GitHub closes-refs are standard), and `{type}({scope}): WIT-XYZ ...` matches Pipekit's commit format rule.

## `pk promote` silently exits when commit range has no Issue-prefix matches

**Status:** New finding from 2026-05-15 RS-Vault canary (post-v2.5.0.1 sync).

**Repro.**

1. Project with `Issue prefix: <X>` set in `method.config.md`.
2. Bundle one or more commits onto `dev` whose subjects/bodies contain no `<X>-<n>` token (ad-hoc bug fix, infra change, dep bump, hotfix without WIT, etc.).
3. Run `pk promote <env>`.

Pre-deploy gate runs and passes. Script then exits `1` with no diagnostic output. PR is not opened. No Linear transitions fire.

**Workaround.** Add an empty commit referencing any issue:

```bash
git commit --allow-empty -m "chore(repo): bundle marker (RS-117)"
```

Then re-run `pk promote` — proceeds normally.

**Root cause.** `bin/pk` opens with `set -euo pipefail` (line 26). The UAT-state refusal block at `bin/pk:1408-1411`:

```bash
local bundled_ids
bundled_ids=$(git log "origin/$target..origin/$source" --pretty=format:%s%n%b 2>/dev/null \
  | grep -oE "${issue_prefix}-[0-9]+" | sort -u)
```

When the commit range contains no matches, `grep -oE` exits `1`. Under `pipefail`, the pipeline exit propagates as `1`. `bundled_ids=$(...)` captures the (empty) output but the failed pipeline trips `set -e`, killing the script before the `if [ -n "$bundled_ids" ]` check that would have safely skipped the block.

`bash -x` trace confirms: last lines emitted are the grep pipeline exiting empty, then immediate `exit 1` with no `ERROR:` printed — the script never reaches a diagnostic branch.

**Precedent in same file.** `bin/pk:528-529` has the exact same pattern with a comment:

> `# || true because under set -euo pipefail, grep with no matches exits 1 and pipefail propagates that through the pipeline, killing the script.`

The workaround was applied at that call site but not in `cmd_promote`.

**Severity.** Medium. Silent failure mode that's easy to misdiagnose as a `gh` or network issue. Doesn't corrupt state — promote just doesn't run. The empty-commit workaround is harmless but cluttery.

**Resolution.** Append `|| true` to both grep pipelines in `cmd_promote`:

- **`bin/pk:1408-1411`** (UAT-state refusal block — the silent-exit site):
  ```bash
  bundled_ids=$(git log "origin/$target..origin/$source" --pretty=format:%s%n%b 2>/dev/null \
    | { grep -oE "${issue_prefix}-[0-9]+" || true; } | sort -u)
  ```
- **`bin/pk:1453-1454`** (Linear-transitions driver — currently reachable only because step 3 is gated on `commits_ahead`, but the same suppression for symmetry).

The `{ … || true; }` form scopes suppression to grep so a later `sort` failure still surfaces.

**Effort.** ~10 min including regression test (`test-pk-promote.sh` — synthetic commit range with no `${issue_prefix}-` matches → verify pipeline doesn't trip `set -e`).

**Anchor.** RS-Vault canary 2026-05-15 (rs-vault project, `Issue prefix: R`).

## `/light-spec` (or other Linear-write skill) requires two-step placeholder push

**Status:** New finding from 2026-05-15 Piper opus session (WIT-394 spec push).

**Observed.** A Pipekit skill that writes specs to Linear via `mcp__claude_ai_Linear__save_issue` is operating under a "mandatory two-step placeholder workaround":

1. **Step 1**: push a placeholder description (e.g. `"_repushing spec…_"`) + state transition.
2. **Step 2**: push the real spec content.

The session log explicitly cited the workaround as "mandatory for this skill" — i.e. it's been encoded as expected behavior in either the skill body or a memory note.

**What's unclear (needs investigation before v2.6.0).**

- Which skill ships this workaround. Likely candidates: `/light-spec`, `/light-spec-revise`, or a versioned variant (`/01-light-spec`, `/02-light-spec-revise`). Grep `skills/` for "placeholder" / "two-step" / "repushing spec" to find the spec-author site.
- Why the workaround exists. Possible root causes:
  - Linear MCP `save_issue` silently drops large description payloads on the first call (rate-limit? indexing race?).
  - State transition + description update in one call don't both land (one wins, the other silently no-ops).
  - Linear API rejects the combined payload with a status code the MCP swallows.
  - Markdown content with specific tokens (code fences? front-matter?) trips a Linear-side sanitizer that the MCP doesn't retry.
- Whether the workaround is still needed. If the upstream issue was fixed (Linear API hardened, MCP added retry) the workaround has rotted into a pointless extra round-trip.

**Severity.** Medium-pending. Every spec push pays a double-round-trip tax (one to Linear MCP, one back) plus produces an extra Linear activity-log entry per spec. Aggregated over a phase's worth of specs that's real noise.

**Resolution path.** Two phases:

1. **Investigation (1-2 hours)**: identify the skill, find the workaround's origin commit, check if the workaround's premise still holds (try a single-call push of a non-trivial spec and observe).
2. **Fix (effort depends)**: either (a) remove the workaround if upstream is fixed, (b) replace with a more targeted workaround (e.g. only chunk if description exceeds a threshold), or (c) document the workaround's necessity in the skill body so future maintainers understand why it's there.

**Anchor.** Piper opus session 2026-05-15 18:06, WIT-394 spec push. Session was running `/light-spec`-equivalent and printed: *"Good — memory confirms the two-step placeholder workaround is mandatory for this skill."*

## Tier system is config-documented but `/work` doesn't honor it

**Status:** New finding from 2026-05-15 Piper review. Surfaced when a reviewer recommended "default to Quick tier for small changes" and we tried to act on it.

**Observed.** Piper's `method.config.md` documents a tier system:

> "/work infers the tier from issue labels (`tier:quick`, `tier:standard`, `tier:heavy`) but always confirms with the human before proceeding."

with a full per-tier gate matrix and a pointer to `pipekit/templates/tier-{quick,standard,heavy}.md`.

But `skills/work/skill.md:517` explicitly says:

> "No tier inference (Quick/Standard/Heavy gone — use `--deep` if you want extra rigor)."

And the tier templates exist in `templates/` but are read by nothing. Setting `tier:quick` on a WIT and running `/work` does nothing different.

**Why it matters.**

- The config makes a promise the code doesn't keep. A reviewer reading `method.config.md` sees tiered gating; a session reading `skills/work/skill.md` sees flat behavior.
- The "Heavy gate-stacking on small WITs" friction the reviewer flagged is real *because* you can't escape to Quick. `Backend: auto` is a related-but-coarser lever (native vs vbw by plan complexity), not a tier replacement.
- The tier docs in `method.config.template.md` propagate to every new Pipekit consumer — they all get the same broken promise.

**Severity.** **Critical with empirical anchor** (revised 2026-05-17 after Piper session-log audit). Originally rated Medium based on the config↔code mismatch alone. Bumped to Critical after surveying Piper's 2026-05-16 sessions: gate-stacking on small WITs is the daily lived experience, not a theoretical concern. See "Empirical evidence" subsection below.

**Resolution options.**

1. **Wire tiers back into `/work`.** Read `tier:*` Linear labels in Step 2 (after fetching the spec), branch on tier in Step 3-onwards: Quick skips spec-review + milestone-readiness + plan-review; Heavy adds security-review + mandatory `/strategy-sync` before close. Standard is no-op (current behavior). Restore Quick → `/06-linear-todo-runner` dispatch path (the runner skill itself still exists — only the routing died). ~4-6 hours including tests.
2. **Delete the tier scaffolding.** Strip Tiers section from `method.config.template.md`, remove `templates/tier-*.md`, update `/work` skill body to make "no tier" explicit in user-facing docs. Update Piper's `method.config.md` to drop the Tiers section. Retire `/06-linear-todo-runner` skill. ~1 hour.

**Recommendation.** Option 1, hard. The empirical evidence (below) is unambiguous: Piper IS doing heavyweight gate-stacking on small WITs because there's no fast lane. Option 2 surrenders the original design AND leaves the user with no answer to "how do I drain Quick Wins fast?"

**Manual bridge until this ships.** See `resources/cmux-parallel-native-batch-prompt.md` — a reusable orchestrator prompt that runs the parallel-native pattern manually via cmux. Empirically validated on Piper 2026-05-17 (5 WITs in 75 min, 1.5-1.8× speedup, 5/5 clean). The prompt is the bridge; this candidate is the proper fix.

**Empirical evidence (Piper 2026-05-16 session-log audit).**

Five sessions, ~13 hours total. All five ran heavyweight gate stacks; zero Quick tier usage. Two smoking guns:

- **WIT-478 PR 1 took 3 hours for one ADR doc PR.** Single ~200-line markdown file (`docs/adr/ADR-004-...md`). Plan-reviewer BLOCKED rev 1 with 5 findings, forced pivot to convention-only approach. `/db-review` (supabase-reviewer) ran. Three reviewer flavors stacked onto a doc-only change. Under a wired Quick tier, this PR would have skipped plan-reviewer + `/db-review` (no SQL, no behavior change) and shipped in <30 min. **3h for one doc = 2.5h of gate overhead on a Quick-class change.**

- **WIT-474 (Production Fee % `14.000000000000002` float drift) labeled "Quick Win, independent, can slot any time" in session 1740's notes — sitting unworked.** Why? Because slotting it requires the full gate stack — plan-verdict + `/verify` per-AC table + `pk ship --review` + plan-reviewer if `--deep` + UAT + `pk done` + manual gh pr merge or `pk done --merge`. For a single-file float-format fix that's overkill that nobody has bandwidth to absorb between heavier work. **Quick Win WITs accumulate as untouched Linear issues** — the visible symptom of the missing fast lane.

**What's also broken, related:** `/06-linear-todo-runner` skill still exists in `skills/`. Zero invocations across all 5 sessions. The skill survived the v2.0.0 cut but the Quick-tier routing died, so the runner is orphaned. Either re-wire it (Option 1) or retire it (Option 2). **Inconsistent state today** — half-deprecated.

**What Piper does today instead.** The "Quick tier" job is being done by manual escape hatches: direct MCP `apply_migration` calls, `gh pr merge` without `pk done`, direct `DELETE FROM supabase_migrations.schema_migrations` via `execute_sql`. Session 2026-05-16_0943 was effectively Quick-class migration-recovery work routed entirely through manual MCP ops because there's no Pipekit fast lane. That works but loses Pipekit's audit-trail + Linear-state benefits for that work.

**Anchor.** Piper review 2026-05-15 + tier↔code audit 2026-05-15 + Piper 2026-05-16 session-log empirical survey (5 sessions, 13h, zero Quick tier usage, 2 smoking-gun examples — WIT-478 PR 1 and WIT-474) + **2026-05-17 cmux-orchestrated parallel-native batch (5 WITs shipped in 75 min wall-clock vs ~90-135 min serial estimate; 1.5-1.8× speedup, 5/5 clean, 3 follow-up WITs filed)**. The batch test proves the parallel-native model works *manually* via cmux orchestration — a wired-back tier system + runner dispatch would deliver this same speedup without the prompt-engineering overhead.

## Stale `02-*-PLAN.md` status blocks cross-WIT edits in fresh worktrees

**Status:** New finding from 2026-05-17 parallel-native batch (cmux-orchestrated, 5 WITs).

**Observed.** Every `pk branch` worktree inherited `.vbw-planning/phases/02-piper-pitch-mvp/02-459-PLAN.md` with `status: ready` — but WIT-459 had shipped 24h prior. VBW's file-guard then blocked every worker in the batch from editing files outside that stale "active" plan's `files_modified` list. ~10 other `02-*-PLAN.md` files have the same stale `status: ready` accumulated from earlier shipped WITs.

WIT-480's worker auto-detected the pattern and wrote the missing `02-459-SUMMARY.md` (commit `cd2b4d3`), which unblocked the rest of the batch. Without that detection, every batch-of-quick-wins would hit the same wall.

**Root cause.** `pk done --merge` cleans up the worktree and transitions Linear state, but does NOT:

1. Write `02-<id>-SUMMARY.md` with the shipped outcome
2. Flip the PLAN.md's `status:` field from `ready` to `complete` (or equivalent)

So plans accumulate as "active" forever. VBW's file-guard treats every non-shipped status as active, and the more shipped WITs you have, the more "active" plans block fresh worktree edits.

**Severity.** High. Burned ~10-15 min of debugging time across 3 workers in the 2026-05-17 batch before the pattern was understood. **Will recur for every batch of Quick Wins until fixed** — making the v2.6.0 tier+runner reinstatement *less valuable* until this lands too.

**Resolution.**

1. **`pk done --merge` writes the SUMMARY.** After the merge confirmation and state transition, write `02-<id>-SUMMARY.md` capturing: WIT ID, PR URL, merge commit SHA, commits-shipped count, brief outcome line. Template can be derived from VBW's existing PLAN.md structure.
2. **`pk done --merge` flips the PLAN status.** Update `02-<id>-PLAN.md` frontmatter `status: ready` → `status: complete` (or whatever VBW's convention is — verify against `vbw:vbw-architect` or PLAN.md template).
3. **(Optional belt-and-braces)** File-guard's "active plan" detection could require an explicit `active: true` marker rather than treating every non-`complete` status as active. That's a VBW change, not Pipekit.

**Effort.** ~1-2 hours for (1) + (2). VBW change for (3) is out of Pipekit's scope.

**Anchor.** 2026-05-17 parallel-native batch — see Piper session log + WIT-480 commit `cd2b4d3`.

## `pk done --merge` doesn't pull master's local `dev` after the remote merge

**Status:** New finding from 2026-05-17 parallel-native batch.

**Observed.** After 5× `pk done <WIT> --merge` in sequence, master's local `dev` was **1 commit ahead** of `origin/dev` and **5+ commits behind** — couldn't fast-forward. The divergent local commit was a docs commit (`72852ad`) that was in master's local dev at session start but is no longer in `origin/dev` (apparently it was rebased or replaced during one of the merges).

Likely cause: PR merges happen on the GitHub side via `gh pr merge`, and master's local `dev` branch never pulls them in. Local state drifts silently from `origin/dev` for the duration of the batch.

**Severity.** Medium. Hides for a long time, then bites when someone tries to ship a fresh feature from master — they discover local dev is stale and have to manually reconcile.

**Resolution.** After `pk done --merge` succeeds:

```bash
git fetch origin
if ! git pull --ff-only origin "$INTEGRATION_BRANCH" 2>/dev/null; then
  echo "WARN: local $INTEGRATION_BRANCH has diverged from origin (cannot fast-forward)" >&2
  echo "  Reconcile manually with: git pull origin $INTEGRATION_BRANCH" >&2
fi
```

Add to `cmd_done` after the existing worktree cleanup step. Warns loudly on divergence rather than silently leaving stale state.

**Effort.** ~15 min including a test fixture.

**Anchor.** 2026-05-17 parallel-native batch end-state.

## Ship `templates/ci/semgrep.yml` + `templates/ci/claude-review.yml`

**Status:** **Two templates, both empirically validated 2026-05-18.** Originally one template (claude-review.yml with Draft-skip); reshaped after the Path 3 decision to add Semgrep as a primary deterministic baseline; the CodeQL plan was dropped after the GHAS gate finding on PR #333.

**History.**
- Piper PR #317 (2026-05-17, commit `7f0a5ae`) — added Draft-skip filter + `ready_for_review` trigger to claude-review
- Piper PR #330 (2026-05-18, merge `3705dfd5`) — dropped `synchronize` from claude-review triggers
- Piper PR #333 (2026-05-18, closed) — CodeQL workflow attempt; revealed GHAS gate for private repos; pivoted to Semgrep
- Piper PR #335 (2026-05-18, merge `3706208`) — added Semgrep workflow (free Community Rules, no GHAS required); ran clean on PR #335 itself in 54s

All four PRs are the empirical predecessors to the canonical templates this candidate ships.

**Observed.** Piper's `claude-code-review.yml` triggered on every push to every PR — 23-commit feature branches like WIT-463 paid ~23 reviews. The `anthropics/claude-code-action@v1` action shipped by the `github@claude-plugins-official` plugin defaults to `pull_request: types: [opened, synchronize]` with no Draft filter. Net effect: heavy credit burn on iteration, when the actual review value is at pre-merge.

**Fix in Piper (already shipped 2026-05-17, PR #317 → commit 7f0a5ae).** Two-line change:

```yaml
on:
  pull_request:
    types: [opened, synchronize, ready_for_review]   # + ready_for_review

jobs:
  claude-review:
    if: github.event.pull_request.draft == false      # + skip Drafts
```

Plus a workflow discipline change: open new PRs as Draft (`gh pr create --draft`), iterate freely without review noise, `gh pr ready <#>` when ready for merge. Empirical: 80-95% credit reduction on heavy-iteration PRs.

**Pipekit ask.** Ship the patched workflow as `templates/ci/claude-review.yml` so every Pipekit consumer that adopts Claude Code Review gets the Draft-skip default. Add a one-paragraph note in `templates/ci/README.md` (creating it if missing) explaining the Draft-PR discipline and `gh pr create --draft` / `gh pr ready` lifecycle.

**Severity.** Medium-high. Every Pipekit consumer using the github plugin's review action hits this same credit-burn pattern unless they explicitly know to add the Draft filter. Shipping the template means the next consumer doesn't have to discover the friction first.

**Resolution.**

1. Create `templates/ci/` directory if missing.
2. Add `claude-review.yml` modeled on Piper's now-fixed file (the canonical version with `ready_for_review` + the `if:` filter).
3. Add a `README.md` documenting the Draft-PR lifecycle + when to use the template.
4. Update `STARTUP.md` (or `method.md`) to reference the template in the "infrastructure setup" steps for new projects.

**Effort.** ~30 min. Lift the patched workflow verbatim, write the README, link from STARTUP.md.

**Anchor.** Piper credit-burn observation 2026-05-17 + PR #317 validation (Draft skipped at 12:18:50, Ready triggered at 12:19:48 — both confirmed empirically).

## cmux numeric keystrokes are ambiguous on Claude interactive menus

**Status:** New finding from 2026-05-17 parallel-native batch (master-orchestrator session controlling 5 worker panes via cmux).

**Observed.** On WIT-474's file-guard gate, the worker's Claude session presented a numbered interactive menu. The master orchestrator sent `"6"$'\n'` to confirm "Chat about this" (visually option 6 in the rendered list) via cmux. The keystroke was silently interpreted as option 4 ("Use a VBW subagent to execute") — Claude's interactive menu treats single-digit keystrokes as quick-pick selectors but its internal index does NOT necessarily match the visual numbering shown in the rendered list (header/separator rows shift the index, options can be conditionally hidden, etc.). The worker proceeded down the wrong path, corrupting the native-only test signal for WIT-474. Pragmatic recovery: shipped via the vbw-subagent path anyway, but the empirical "does parallel native scale?" data point for that WIT was only partial.

**Why it matters.**

- Every cmux master-orchestrator session that drives worker Claude panes through interactive menus is exposed to this. Numbered menus *look* unambiguous; they aren't.
- The failure is silent — the worker doesn't know it got the wrong option, the orchestrator can't tell from `read-screen` whether the menu's numeric mapping matched the visual one.
- The corruption is one level removed from the actual work: the worker still produces clean output, just from the wrong starting path. Easy to miss without explicit cross-checks.

**Canonical pattern (needs documenting in `pipekit-cmux.md`).** Use highlighted-option confirmation, not numeric selection:

```bash
# Correct: confirm the currently-highlighted option (default: first)
cmux send-key --surface <ref> enter

# Correct: navigate to a different option, then confirm
cmux send-key --surface <ref> down
cmux send-key --surface <ref> down
cmux send-key --surface <ref> enter

# WRONG: never send numeric strings to a Claude interactive menu
cmux send-text --surface <ref> "6"          # ambiguous — may not map to visual option 6
cmux send-text --surface <ref> $'6\n'       # same ambiguity
```

This makes intent explicit (you're navigating + confirming a highlighted option, not betting on numeric mapping), is robust to menu re-ordering or conditional options, and matches how a human operator would drive the same menu.

**Severity.** Critical (orchestrator-only). Doesn't affect single-pane interactive sessions where the human is making the selection. Bites cmux-orchestrated batches specifically — and the v2.6.0 tier+runner work (top scope item) will increase the volume of those batches, making this more load-bearing not less.

**Resolution.**

1. **Add to `pipekit-cmux.md`** — new "Interactive menu discipline" section with the canonical pattern above + a "never do this" example + a brief explanation of why numeric mapping is unreliable.
2. **(Optional)** Add a lint/guard in any orchestrator prompt/skill that's known to drive cmux panes (`resources/cmux-parallel-native-batch-prompt.md` is the existing one) — reject numeric `send-text` calls aimed at interactive menus, suggest the `send-key enter` pattern.

**Effort.** ~30 min for (1); ~1 hour for (2) if pursued.

**Anchor.** 2026-05-17 parallel-native batch, WIT-474 file-guard gate — see Piper session log §"Decisions / findings" point 3 + QA trail row "File-guard | WIT-474 | **Mistake** — sent '6' got option 4 (vbw-subagent escalation)".

## Replace claude-review as the default "outside reviewer"

**Why OpenAI/Microsoft are disqualified — the IP-absorption pattern.**

The risk isn't model-training (OpenAI's API has had a "no training on customer data" default since March 2023 — that's contractually solid). The risk is **organizational learning that no contractual guarantee covers**: OpenAI/Microsoft employees, product teams, and roadmap planners observe customer patterns and decide what to build next. Examples:

- **ChatGPT** itself emerged after watching what people built on the GPT-3 API
- **Code Interpreter / Advanced Data Analysis** followed observing user patterns in custom integrations
- **The GPT Store / Custom GPTs** effectively absorbed the OSS LangChain-style ecosystem within months of seeing it
- **Operator** (browser agent) shipped after observing how third parties stitched browser automation into agentic loops
- **GitHub Copilot** was trained on a corpus that included third-party patterns, with the Doe v. GitHub class action still adjudicating where the line is
- **Microsoft's embrace-extend-extinguish pattern** (Netscape, Java, Office formats; more recently VS Code's "first-party extension" pattern that observes and absorbs popular community extensions) is a multi-decade documented behavior

For a domain-specific platform whose moat is implementation cleverness + novel workflows, shipping code through an OpenAI/Microsoft pipeline is shipping organizational learning *into the company most likely to build a competing product*. The contract doesn't address this; only vendor-selection does.

**Why Claude is acceptable risk (with eyes open).** Anthropic is also a frontier-model AI company that could in theory pivot into vertical applications. The reasons to weigh them lower (not zero):

- Different go-to-market focus to date (infrastructure > vertical applications)
- Shorter track record of "observe-and-repackage" — partly because shorter history, partly because their public narrative emphasizes research + safety over consumer-product velocity
- Constitutional AI / safety-first positioning makes consumer-vertical pivots more reputationally costly
- Commercial terms explicitly exclude training on API data — same as OpenAI API, but Anthropic hasn't had OpenAI's pattern of policy reversals

**The only truly clean path** is local inference on open-weights models (Llama, Qwen, DeepSeek, Mistral self-hosted). That's a real option but adds significant friction. Not chosen for v2.6.0; documented here as the "if we ever care more about this, here's the escape hatch" path.

**Why Path 3 (Semgrep + Claude) — recap.** Semgrep is rule-based (no observational learning, no IP-absorption surface at all). Claude carries moderate-but-acceptable risk under the framing above. Claude stays as the semantic reviewer it's good at (and empirically caught the only must-fix bugs on PR #331 — see "Key empirical findings" above).

Semgrep delivers the same Path 3 thesis on private repos for free, via a single self-contained workflow file with no repo-level settings required.

## `pk ship --draft` default + ready-flip gesture

**Status:** New finding from 2026-05-18 reviewer-strategy discussion (uncovered while validating today's PR #330 trigger config).

**Observed.** `pk ship` opens PRs **as Ready** unconditionally (`bin/pk:640` calls `gh pr create --base ... --head ... --title ... --body ...` with no `--draft`; line 627 does the REST equivalent). There's no `gh pr ready` call anywhere in `bin/pk`. Pipekit does not manage Draft state today.

**Why this matters now.** PR #330 (merged 2026-05-18) trimmed Piper's `claude-code-review.yml` trigger to `[opened, ready_for_review]`. Under current Pipekit behavior:

- `pk ship` fires `opened` → claude-review runs **once**.
- `ready_for_review` **never fires** because the PR was already Ready from the start.
- Net: PR #330 effectively limits Piper to "1 review per PR open" — which is the minimum, but the `ready_for_review` trigger is dead code.

The user's described desired flow ("open PR → review fires, I work, work, work, no problem, ready to ship → it reviews again") **requires** Draft handling. Open as Draft → no review during iteration → flip to Ready when shipping → 1 review at the pre-merge moment. Without `pk ship --draft`, this flow is impossible through Pipekit's interface (only via manual `gh pr create --draft` + `gh pr ready`, which bypasses pk's Linear-state transitions).

**Resolution options.**

1. **`pk ship` opens Draft by default; `pk ship --ready` opts out for one-shots.** Then a new gesture flips Draft → Ready. Two options for that gesture:
   - (a) **New `pk ready <ID>` command** — explicit. Linear stays in UAT (no state change). PR flips Draft → Ready. Fires `ready_for_review` → outside reviewer runs.
   - (b) **`pk done --merge` flips Draft → Ready as a precondition to merging** — implicit. Merge wouldn't proceed against a Draft, so `pk done --merge` flips first, then merges, then runs the existing post-merge work. Risk: tightly couples "I'm ready for review" with "merge it now" — no review-then-fix loop unless user manually flips back to Draft.
2. **`pk ship --draft` flag (opt-in to Draft);** default stays Ready. Less ambitious. Doesn't change the default behavior, but lets consumers who want Draft discipline use it without bypassing pk. Lower value because most consumers won't discover the flag.

**Recommendation.** Option 1(a) — `pk ship --draft` default + new `pk ready <ID>` flip command. Mirrors the existing verb structure (`branch` / `ship` / `done` / `promote` — adds `ready`). Keeps "I want a review now" as an explicit user gesture, separable from `pk done --merge`. The `--ready` opt-out on `pk ship` exists for tiny one-shot WITs where iteration won't happen.

**Severity.** Medium. Today's PR #330 is doing useful work even without this (1 review per PR open). But the "ship-time review" half of the desired flow doesn't exist in Pipekit until this lands. Bumps to High if the outside-reviewer decision above lands on a model where the `ready_for_review` trigger is the primary signal.

**Effort.** ~1-2 hours:

- `cmd_ship` in `bin/pk`: add `--ready` flag (and inverse: default behavior changes to Draft); pass `--draft` to `gh pr create` unless `--ready`.
- New `cmd_ready` function in `bin/pk`: takes `<ID>`, finds PR by branch, runs `gh pr ready <PR#>`, no Linear transition (UAT → stays UAT). Includes the same idempotency checks as `cmd_branch` and `cmd_ship`.
- Update `skills/work/skill.md` and `RUNBOOK.md` to document the new Draft → Ready lifecycle.
- Update `method.config.template.md` if there's a "PR lifecycle" section worth touching.

**Coupling.** See "Replace claude-review as the default outside reviewer" above — both are about the "outside reviewer fires at the right moment" workflow. They should land in the same v2.6.0 batch so the trigger config, the reviewer choice, and the Pipekit gesture are aligned end-to-end.

**Anchor.** 2026-05-18 reviewer-strategy thread (this session) + `bin/pk` line 640 audit confirming no `--draft` / no `gh pr ready` calls. Piper PR #330 (merged 2026-05-18 at 12:20:23 UTC) is the predecessor that made this gap visible.

## `pk branch` doesn't symlink `.envrc` into new worktrees

## `pk branch` runs `pnpm install` automatically instead of hinting

**Status:** Surfaced 2026-05-23 — coupled with #14 (both are `bin/pk` worktree-setup polish).

**Observed.** `bin/pk:873-892` (added 2026-05-14 via commit `16e69ac` for F8) prints a hint after every `pk branch`:

```
⚠️  Fresh worktree — install deps before first test:
     (cd $wt_path && pnpm install)
```

The hint fires unconditionally in Node projects because worktrees inherit tracked files but not gitignored `node_modules/`. Pipekit already knows the package manager (lockfile sniffing at lines 880-886) and that the install is always the next required step. The current design makes the human type a command Pipekit could run.

**Fix.** Auto-run the install in foreground, with a `--no-install` opt-out flag for the cases where deps are already cached or the user is doing something custom.

```bash
pk branch <ID>                # installs by default
pk branch <ID> --no-install   # skip (cached deps, spec-only worktree, etc.)
```

Replace the warning hint with a progress line during install (`Installing deps via pnpm...`) and surface the `--no-install` flag in the "To enter:" output block so the opt-out is discoverable:

```
Done.

To enter:
  cd $wt_path && claude --dangerously-skip-permissions

(use `pk branch <ID> --no-install` next time to skip the dep install)
```

**Severity.** Low-Medium — UX polish. The install is always needed; making the human type it is friction. Background-install was considered and rejected: reintroduces the original race (`/work` hits half-installed `node_modules/` mid-flight), which is exactly what F8's hint was meant to prevent.

**Effort.** ~30 min. Replace the warning block (lines 878-892) with `pnpm install` invocation gated on `$skip_install`, add `--no-install` arg parsing at the top of `cmd_branch()`, append the discoverable opt-out hint to the final output.

**Coupling.** Ship with #14 (`.envrc` symlink). Both touch `cmd_branch()` worktree-setup; both are paper-cut polish without behavioral risk.

**Anchor.** 2026-05-23 session — user observed the hint firing on every `pk branch` and proposed auto-install with discoverable opt-out as the obvious cleanup.
