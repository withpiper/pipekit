## Decisions / findings (worth remembering)

1. **Stamp calibration-version rule.** Stamps record the release the doc is *calibrated to*, not the release we last typed into the doc. Drift between stamped version and current release is the signal. Bumping every doc to current on every release would erase the signal — only bump docs you actually edited. The constitutional docs (method.md / RUNBOOK.md / GUIDE.md) are the exception: they describe current behavior and should always carry the latest version.

2. **First Explore agent's "all clean" was overconfident.** The audit-style agent (asking "is this clean?") returned all-green for 14 files. Spot-checking revealed real stamp drift (SOPs claiming 2026-04-08 dates while git showed 2026-05-09/13 edits) and missed `--confirmed` flag gaps. Lesson: trust-but-verify applies to subagent reports even when they're confident. A polish-oriented brief ("what would you change?") surfaced what an audit-brief ("is this drifted?") missed — different agent framings yield different findings on the same files.

3. **drift-check.sh has known false positives via naive substring matching.** It flagged `/pk-next`, `/pk-status`, `/launch`, `.pipekit/journal/` as unresolved references — but each appears inside an anti-pattern warning, v1-history note, or deletion notice. The drift signal would improve materially if the script learned "do not", "v1's", "deleted/retired" suppression patterns. Logged as a future improvement; not fixed in this release.

4. **Release ceremony pays off even for doc-only changes.** Considered shipping the polish as a plain docs PR (no version bump) — but stamping everything `v2.4.3.1` while shipping on 2026-05-14 leaves a small lie in the calibration version. Cutting v2.4.3.2 was the honest move and got consumers a clean tag to pin. The Release Checklist I added literally describes this scenario.

5. **VBW_COMMANDS.md is not ours to update.** When the polish pass considered regenerating it from current `/vbw:help`, the user flagged: external snapshot, external version. Re-snapshotting on every VBW release would be churn for content we don't own. Document as a snapshot, stamp with the Pipekit version when last touched, leave the body alone unless VBW ships a breaking change worth re-snapping for.

6. **Auto-tag-release.yml workflow worked first try.** PR title containing `v2.4.3.2` → tag fired on merge automatically. Validates the workflow that was added recently to close the gap where v2.3.3 and v2.4.1 forgot the manual tag step.
