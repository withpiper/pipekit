## Findings (real defects)

### F1 — `/work` skill calls non-existent `bin/pk pk_config` subcommand

**Severity:** Medium (every `/work` invocation eats a failed bash + recovery cycle)
**Scope:** Doc-only patch
**Where:** `skills/work/skill.md:65`, `:68-71`, `:79`, `:478`

The skill body documents reading config values like this:

```bash
BACKEND=$(bin/pk pk_config "Backend" "vbw")
DEEP_FLAG=$(bin/pk pk_config "Default deep flag" "false")
```

But `bin/pk` only exposes `pk config` (subcommand). `pk_config` is an internal shell function reachable only when `bin/pk` is *sourced* (confirmed at `bin/pk:1938`: *"Skip main when sourced (lets tests exercise helpers like pk_config directly)."*). First `/work` config read crashed with `Exit code 1: Unknown subcommand: pk_config`. Worker self-recovered by retrying with `pk config "Backend" "vbw"` and got correct values.

`/verify` skill body uses the correct `pk config <key> <default>` form, so **this defect is `/work`-specific, not systemic**.

**Fix:** Update `skills/work/skill.md` to use `pk config "$key" "$default"` (or, if `bin/pk pk_config` is intended to be a subcommand, expose it from `bin/pk`'s main switch — but the simpler fix is the doc patch).

**Why v2.4.3.2 missed it:** The doc-polish pass's stamped-docs inventory and drift-check.sh scan check for stale paths and removed-skill references. They don't validate command examples against `bin/pk`'s actual subcommand surface. Worth adding a `check-pk-command-examples.sh` companion to drift-check, or rolling that check into drift-check itself.

### F6 — `/work → /verify → pk ship` auto-chains without human pause (methodology question)

**Severity:** Methodology decision needed before classifying as bug
**Where:** Auto-chain messages in worker output:
- "✓ /work complete for WIT-456 — auto-running /verify"
- "✓ /verify Pass — auto-running pk ship"

The chain stopped at `pk ship` (correct hard gate per v2.4.3 — Linear → UAT, no `pk done` / `pk promote`). But intermediate gates were never human-confirmed:
- No "diff looks good?" pause before `/verify`.
- No "want to ship now?" pause before `pk ship`.

WIT-451's fix language ("auto-cascade past UAT") technically permits "to UAT but not past." But that creates an awkward shape: the human can't review the implementation before it lands in a PR. If `/work` produces a wrong-direction diff, `pk ship` will have already opened the PR by the time the human looks.

**Question for methodology owner (user):** Is auto-chain `/work → /verify → pk ship` intended? Three options:
1. **Keep current behavior.** Chain is a feature, not a bug. UAT is the only gate. Document the chain explicitly in `/work` skill so humans expect it.
2. **End `/work` at the commit.** Worker says "commit landed — run `/verify` when ready" and stops. Adds human review point but slows the loop.
3. **Pause only before `pk ship`.** `/work → /verify` chains (both are read-only-ish on shared state), but worker stops with "verify passed — run `pk ship` to open PR." Splits the difference.

Recommendation: option (3). The diff is observable in commit form between `/verify` and `pk ship`, and `pk ship` is the first irreversible step in the chain (pushes to remote, opens PR, mutates Linear). The user benefit from a confirm-before-push is high; the latency cost is one keystroke.

**Fix options:**
