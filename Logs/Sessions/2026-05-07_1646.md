## Decisions / findings (worth remembering)

1. **The bug pipeline's reason-to-exist is the regression-test-first gate.** Without it, `/pk-bug` is just `/work` with extra steps. The whole skill exists to enforce: failing test must exist before fix code, test commit lands FIRST on the branch (audit trail), no fix without something that would have caught it.

2. **Linear is the source of truth for resume routing — and routing must key off `statusType`, not display name.** The first run hit this immediately when rs-vault returned status `Parked` (a `statusType=backlog`) instead of `Backlog`. Generalizing to `statusType` makes the skill durable across projects with custom workflow names.

3. **Use Linear's native `priority` field, not custom severity labels.** Reduces ceremony, makes filtering work natively, no per-project label provisioning. Mapping: Urgent=critical, High=high, Medium=med, Low=low.

4. **Coworker Mode does not belong in `method.md`.** Considered formalizing "Claude as project teammate" as an explicit Pipekit concept (the user found ad-hoc deliberation useful). Pressure-tested with antiview and rejected — formalizing creates: stale-context confidence, second source of truth bypassing pipeline gates, Trojan horse for AI overreach, worldview commitment that consuming projects inherit. The value is emergent from existing primitives (CLAUDE.md, rules, memory, MCP). Don't bottle it.

5. **Dropped the proposed Skill Development SOP page.** Decided the build-local → dogfood → promote pattern is captured inline in `/pk-bug`'s Origin section. A dedicated SOP would be a doc-rot magnet describing what's already happening.

6. **Cross-project execution is a smell.** When working in pipekit and the user has another Claude session live in rs-vault, do not run write operations on rs-vault from this session — even if invited. I crossed this line mid-session by running the dev→main merge for rs-vault PR #162 here. User flagged it. Saved as `feedback_cross_project_execution.md` memory. Read-only checks across repos still fine; writes belong in the target project's session.

7. **`/work` auto-branch is strictly better than the manual step.** The existing pipeline forced `pk next` → user copies ID → `pk branch RS-XXX` → `/work RS-XXX`. After observing `/pk-bug` auto-branched and the user noted it was cleaner, modified `/work` to do the same when invoked from `dev`/`main`/`beta`/`master` with an explicit ID. The manual `pk branch` step is now optional, not required.
