## Decisions / findings (worth remembering)

1. **The competitive scan validated the standing thesis rather than overturning it.** All four frameworks evaluated (264k–7.5k stars) were real and well-resourced, but none implement Pipekit's specific hard-enforcement primitives (adversarial DOUBT-loop, sha-matched sentinels, frozen-migration invariant). GSD converged independently on the same 3-cycle-then-escalate cap — evidence the design is sound, not novel.
2. **Step 5's sensitive-content grep bug was a classic whole-diff-vs-added-lines mistake**, live since the auto-trigger was written — a file merely *listing* `CREATE POLICY` in a context line tripped mandatory antagonistic review. Flagged by PIPER-494, never actioned until this session's log sweep.
3. **`pk_linear_tier`'s silent default was a genuine ambiguity bug, not just a style issue.** "No tier: label" and "Linear unreachable" produced the identical observable output (`"standard"`), so `/verify` couldn't distinguish a deliberately-labeled issue from a guess. Fixed by having the function return empty and pushing the fallback + warning to the caller — same shape as `pk_verify_sentinel_for_head`'s design.
4. **A CLI's own agent-auto-detection can make scripted output format caller-dependent.** Verified against the installed Supabase CLI (`--agent`, default `auto`) and anchored to a real SiteLine incident (PIPER-533) rather than asserted from memory — this is exactly the class of gotcha `pipekit-tooling.md`'s "verification method must see the failure" section exists for.
5. **The `/strategy-sync` timing question turned out to be a three-way doc contradiction, not a simple ordering question.** `templates/tier-heavy.md` described a hard pre-`pk ship` gate that `bin/pk` never implements (pure vaporware — grep confirmed zero matching code); `skills/work/SKILL.md`'s heavy-tier reminder said "before `pk done`," printed right after the Draft PR opens and before anything's reviewed; only the `pending-strategy-sync` marker (set by a documented **post-archive hook**, i.e. `/phase-plan --next`) reflects the live, initiative-level mechanism. Trusted the user's instinct over the more prominent (but unmechanized) doc text.
6. **A downstream `claude-review` on a doc-only sync PR caught a real gap** the same cleanup pass missed — `templates/tier-heavy.md`'s Required-artifacts bullet still read as an unqualified pre-close requirement, 11 lines above the sentence explicitly saying otherwise. Treated as a legitimate finding (verified against the file before acting), not rubber-stamped.
7. **Two consumer-repo mistakes, both caught before merge.** (a) Committed two of the user's own pre-staged, unrelated files (a session log, a PDF) into a sync commit by using `git add <files>` after they were already staged — `git add` adds to the existing index, doesn't replace it. Fixed via `git rm --cached` + a new commit before opening the PR. (b) Branched directly in SiteLine's primary checkout for a sync instead of a worktree, on the reasoning that it "looked clean" — moved whatever concurrent session was using that checkout off `main` momentarily (a new session log appeared while on the branch). Switched back to `main` and restored the original staged state, then used worktrees for every sync after. The dirtiness of a checkout isn't the signal that matters; a shared primary checkout always risks a concurrent session regardless of current cleanliness.
