## Decisions / findings (worth remembering)

1. **Codex rejected as a reviewer; the trial still paid for itself.** Pre-registered scoring: Case A (a known Claude miss) → **MISS**, zero findings on the target surface. Case B (noise test) → ~5 duplicates and ~4 restatements of the PR's own documented residuals, all at **confidence 100**. Its confidence tracks "I found supporting text," not "this is unflagged" — which would poison `/pr-fix` §3.4 triage, where confidence drives surfacing. Vendor rule ([[feedback_vendor_ip_absorption]]) never needed reopening.

2. **The trial's first run was contaminated, and nearly got scored.** A `git worktree` detached at an old commit **still shares the parent repo's refs**, so the reviewer read the follow-up fix PRs and cited them ("the later PIPER-554 migration confirms both defects") at confidence 100. Real isolation needs a separate `--no-hardlinks` clone with all refs deleted, reflogs expired, `gc --prune=now`. This became a new `pipekit-tooling.md` clause: the existing rule asks whether a check can *miss* a failure; it never asked whether the check can **cheat**.

3. **The ship→merge window was structurally unguarded.** `pk ship`'s sentinel gate is point-in-time. SiteLine PIPER-490: verify PASS at `eca992bb`, ship 21:55Z, then `4f47b160` rewrote **72 lines of the RLS migration's authorization predicate** at 22:28Z, merged 05:41Z. The PR review that read the evidence quoted its sha verbatim and never noticed HEAD had moved.

4. **I shipped v4.27.0 with two defects and both were found within hours.** (a) `unreachable` failed open, so a rebase right before `pk ready` defeated the gate — caught by SiteLine's automated review. The deciding argument was *consistency*, not fail-closed instinct: `pk ship` demands an exact sha match, so a rebased branch can't ship at all; allowing the Ready flip made the new gate **looser than the one it reinforces**. (b) The lookup globbed the working tree only, and `pk done` runs from the parent repo **by design** — so its post-merge report **never fired on any invocation**. Defect (b) *masked* (a): fixing the class list alone would have changed nothing observable.

5. **PIPER-490 was NOT force-shipped — retracting an earlier claim I made twice.** It was inference from absence. `/verify` did reach PASS (`f9eb29517`), there is no `--force` Linear comment, and `bypass.log` is empty. The sentinel was written to disk, honestly consumed by `pk ship`, never staged, then destroyed with the worktree by `pk done`. This is exactly why the lookup must check **both** the working tree and the branch tree.

6. **Prose templates drift; heredocs don't — with a number attached.** Two files in the same skill, written seconds apart, differing only in generation method: heredoc-written `verify-complete.md` carried a `sha:` line in **191/192** committed files; prose-rendered `reality-check.md` in **167/195** — and *rising*: 8% missing in June, 24% July, 33% August. The template was never wrong; it always said `- sha: <git rev-parse HEAD>`. Nothing in a prose template *fails* when a line goes missing. Also found `$STATUS` was consumed by Step 8 but assigned nowhere.

7. **Recommendation reversed on inspection — and the first instinct would have shipped a fourth defect.** I proposed making `/verify` commit the sentinel. Checked first: all 192 committed sentinels record their commit's **parent**, because stamping HEAD then committing moves HEAD. Making `/verify` commit it would have broken `pk ship`'s exact-match gate on every ship. The narrow fix (deterministic `sha:` in `reality-check.md`) was the right target.

8. **The release workflow had a script-injection vector, found only because a release failed to tag.** `auto-tag-release.yml` interpolated the PR title into a shell string; v4.27.2's apostrophe in "reality-check.md's" closed the quote and the release merged **untagged**. Because `${{ }}` substitutes before bash parses, a crafted title runs arbitrary commands in a job holding `contents: write`. `templates/ci/` was already safe → **no consumer inherited it**.

9. **Two verification methods gave false clean results this session.** An awk scan for the injection pattern reported clean while a known instance existed; a `BASH_REMATCH` test run under zsh printed "✓ extracted v" on an empty match. Both were caught only by asking what a failure would have looked like. Always re-run bash-semantics checks under `bash -c`.

10. **`~/.local/bin/pk` symlinks to SiteLine's *parent* checkout**, so worktree sessions pick up a new `pk` the moment SiteLine's `main` is pulled — no per-worktree action. Merging the sync PR is not enough on its own; the local checkout must be pulled for the symlink to serve the new binary.
